## The five-zone display model — VERIFIED WORKING, do not redesign
```
Zone 1  event message + number + ordinal    top row
Zone 2  recipient name                       bottom row, centered
Zone 3  decorative fill                      flanks zone 2, sized by
                                             (zone1.width - zone2.width) / 2
Zone 4  backdrop elements                    density-derived from zone 3
Zone 5  bookends                             absolute left/right edges
```

## Data flow AS BUILT (configurator, 2026-10-23, PRs #47-#50)
```
wizard start  -> getAvailabilitySnapshot()  server action -> yce_availability_snapshot
                                            (stock + blocking holds, today-1..+180;
                                            this session's holds marked `mine`)
step 1        -> dayStatus() per calendar day: closed (booking rules) / full
                                            (displayFits on that window) / open
step 2        -> buildablePairs()/pickerOptions() per line; the second line
                                            only sees what the first leaves
              -> calculateLayout()          manifest resolves PNGs; every ZoneSign
                                            gets a catalogKey; extras from free stock
              -> createBookingHold()        auto, 800ms after the layout settles;
                                            15 min while anonymous, 60 after contact
step changes  -> touchBookingHold(stage)    slides the hold by the stage's minutes
place order   -> /api/orders/create -> yce_convert_hold_to_order
                                            (order hold + order_signs; order
                                            rolled back if it fails)
```
The browser-side check is a preview; the hold is the real check (same
rule in `yce_sign_availability`, under the agency lock). A refused hold
toasts, clears the last line's color and reloads the snapshot.
Inventory = `agency_inventory.quantity` per `sign_library` row; letters
are one row per manifest asset (`asset_key` = manifest id), signs with no
art yet are `mock-*` rows (`catalog-keys.ts`). All test agencies hold 20
of each (seed `migrations/20261007_seed_placeholder_sign_library.sql`,
generated by `scripts/generate-sign-seed.mjs`). Letters, numbers,
ordinals and punctuation are only offered in style/color pairs with
enough free stock; decorations, backdrops and bookends are random but
drawn only from free stock (`extrasStock` / `takeFree`).

**Availability** (`yce_sign_availability`) for rental days [start, end]:
quantity - live temporary holds overlapping the range - active order holds
with `rental_start <= end`. Order holds have no end: signs stay out until
released by check-in (`yce_check_in_order`) or cancellation
(`yce_cancel_order`), or by hand with `SELECT yce_release_order_hold(id)`. Every write takes a per-agency
advisory lock. A new temporary hold replaces every live temporary hold
of the same wizard `session_id` (server-side; a refused one keeps them). The `yce_*` functions are granted to `service_role` only.
Rental range = delivery (event day - extra days before - `setupDays`)
through pickup (event day + extra days after + `teardownDays`), UTC
calendar days of the local-noon event date. Order cutoff: end of day,
`orderCutoffDays` before delivery, in the agency's
`operating_hours.timeZone` else the customer's zone. All in
`features/booking/booking-rules.ts`; extra days are picked in Event
Details so the window is known before the configurator holds anything.
Hold creation is rate-limited per hashed client IP (3 live per agency,
30 per 10 min) inside `yce_create_booking_hold`.

**Not used by the booking side:** `agency_inventory.available_quantity` /
`allocated_quantity` / `deployed_quantity` - counters from the dashboard
side that know nothing about dates or holds. `features/inventory/actions.ts`
`checkBulkAvailability`/`createSoftHold` (agency side, URL-tenant based,
createSoftHold inserts holds without an id and would fail) are unrelated.

## SignStyle: the dev/prod split
`SignStyle.dev` = colored blocks keyed by sign type. **Deliberate
placeholder for distinguishing sign types visually, not unfinished
work.** `SignStyle.prod.imageUrl` = real image. `LetterStake` (and
`DecorationSign`/`BackdropElement`/`BookendSign`) branch on whether
`prod.imageUrl` is set. **Live since commits `742320c`/`e41f821`**: the
PNG manifest populates `prod.imageUrl` for zone1/zone2 letters and Zone 3
Stars/Heart via `resolveAsset()` calls in `layout-calculator.ts`. No new
field was needed — this was designed in from the start.

## Known renderer bug: stakes escape the preview box
`DisplayGrid` wraps each character in `flex-shrink-0`, and
`getResponsiveSize()` returns a `clamp()` based on VIEWPORT width with
no awareness of character count. Long messages overflow and get clipped
by `overflow-hidden`. The zone math is fine.
Fix: derive one scale factor from container width ÷ row width in inches
(`layoutRow()` / `pxPerFoot()` in `services/sign-assets.ts`), so
character count drives size. Same code path that makes real PNGs render
at correct relative widths and align on baseline rather than image
bottom.

## Zone 3/4/5 extras — real art, picked by theme, occasion, holiday or hobby
Since 2026-10-25 every decoration, backdrop and bookend the calculator can
place has full-color art: SVGs in `tools/sign-generator/decorations/`,
die-cut like the letters by `generate_decorations.py`, in the manifest as
style `"art"` (colorway = kind, character = slug; `resolveArt()` +
`artSlug()` in `catalog-keys.ts`). They are one version each - the color
pickers only apply to letters and numbers. Stars/Heart stay shape assets in
the 7 letter colorways (`DECORATION_SHAPE_KEYS`). Each extra is a
`mock-*` sign_library row with stock for the six test agencies
(`scripts/generate-sign-seed.mjs`); selection only draws from free stock.

What gets picked (`layout-calculator.ts`):
- **Hobbies** picked: `rankDecorationsByHobbies()` - the keyword matches,
  the matches again, then everything else (so an out-of-stock hobby still
  leaves candidates).
- **No hobbies**: a random pick from `getThemeDecorationPool()` - the
  picked Theme's pool; for Holiday, the holiday nearest the event month
  (`holidayPools`, needs `eventDate`); with no theme (or Classic), the
  message's occasion (`occasionPools`: birthday, grad, anniversary, welcome
  home, get well, congrats); else the classic party set.
- Backdrops cycle `backgroundPool`; bookends are a balloon bouquet each side.

## Smart configurator (Theme/Style/Color/Hobby) — STYLE/COLOR BUILT, THEME NOT
Design conversation from 2026-09-16 (pointer in STATE.md). Style +
Colorway (the hard constraint) shipped 2026-10-23 as "Data flow AS
BUILT"; blockers 1 and 2 below are done for the placeholder library
(`sign_library.character/style/colorway`, 20 of each per test agency).
Theme, occasion and hobby pools for the extras exist (see "Zone 3/4/5
extras" above), but as separate rules, not one weighted score. The
intended model:
- **Message / recipient name**: free text, decoupled from style/colorway
  — any words render in any style/colorway the agency has.
- **Style + Colorway**: hard constraints sourced from `agency_inventory`
  — a customer can only pick combos the agency actually owns (e.g. one
  agency has red/green/gold letters, another has purple/green/blue).
  These determine which letter assets get used for zone1/zone2, plus a
  real sufficiency check: enough of each needed character, in that
  style/colorway, to spell the whole message + name.
- **Theme**: derived from the selected message itself (one message may
  carry one or more theme tags, e.g. "Happy Birthday" -> birthday-ish).
  A *weight*, never a filter — it never removes options, only biases
  scoring.
- **Hobbies**: a second, independent weight, additive to Theme.
- **Zone 3/4/5**: selected by weighted search combining Theme-weight +
  Hobby-weight against the agency's actual inventory for those
  categories — generalizing the rank-everything/never-exclude pattern
  already shipped for Zone 3 decorations (above) to also cover
  backgrounds/bookends, with Theme folded into the score instead of
  today's hobby-only weighting.

Blocked on, in order:
1. `sign_library` schema for letters — `character`/`colorway`/
   style-family columns, additive/nullable so existing pre-made-board
   rows are unaffected.
2. Per-agency inventory seed data — which agency owns which
   style/colorway combos. A business decision, not something to invent.
3. Message -> theme taxonomy — a first version is hardcoded in
   `layout-calculator.ts` (`occasionPools`); still open whether it should
   be DB-driven or per agency.
4. Scoring formula for combining Theme-weight + Hobby-weight — not
   specified yet (additive sum vs. weighted, tie-breaking rules).

None of this is buildable without (1)-(3) being decided first — they're
data/business decisions, not implementation details.

## Inventory holds — BUILT 2026-10-07
See "Data flow AS BUILT". Spec origin: triggered on preview generation,
1 hour, session-based, automatic cleanup. User decision 2026-10-07: two
hold types - `temporary` (configurator) and `order` (until signs are
checked in or damaged out). Temporary holds expire after inactivity:
15 min while the customer is anonymous, 60 once they've given contact
details (`HOLD_MINUTES` in `actions.ts`, `p_ttl_minutes`; was 1h for
all until 2026-10-23). Columns added:
`inventory_holds.hold_type/rental_start/rental_end/released_at/
release_reason`; `expires_at` is NULL for order holds. Cleanup cron
`/api/cron/clear-expired-holds` (daily) is housekeeping only.
Alternatives on conflict: nearby open days are offered; the preset
alternatives list (`display-options.ts` `alternatives`) is empty pending
the owner's short-presets idea.

## Tenant guard (app-level: RLS is only a deny-all backstop)
RLS is ON for every public table (YCE's since 2026-10-19, all of them
since 2026-10-30) but YCE tables have no policies: the public anon key
reads nothing, and the app's service-role client bypasses RLS entirely.
So RLS isolates no tenant from another; the checks below are the only
tenant isolation. Dashboard pages check `getUserById(auth().userId).agency.slug === URL
slug`. Anything callable without a page — `'use server'` actions, API
routes — must check membership itself: `requireAgencyMember(agencyId)`
in `features/auth/guards.ts`, or the `user.agency_id !== agencyId` check
the `/api/agency/*` routes use. `getCurrentTenant()` resolves the agency
from the URL and proves nothing about the caller. Public routes must
never return a raw `agencies` row: it holds `braintree_private_key`.

## RLS — the correct policy pattern, for when hardening happens
The original spec had this right and the live database drifted from it.
The only live policies (`users_read_own`, PantryPro's `vendor_invoices` /
`vendor_payments`) use `auth.uid()`, which is ALWAYS NULL under Clerk. The
spec's pattern resolves the Clerk subject claim instead:
```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY agency_isolation_orders ON orders FOR ALL USING (
  agency_id = (SELECT agency_id FROM users
               WHERE clerk_user_id = auth.jwt() ->> 'sub')
);
```
Requires Clerk configured as a Supabase third-party auth provider so the
JWT reaches Postgres. Do NOT write policies against `auth.uid()`.

## Pricing path
`agencies.pricing_config` (JSONB) -> `/api/agency/financial-settings`
-> `FinancialManagementSection.tsx` (agency settings UI). Complete.
Booking side: `[agency]/booking/[[...path]]/page.tsx` reads
`pricing_config` server-side via `parseBookingPricing()` and passes
`agencyId` + `pricing` into wizard context; every step totals with
`calculateBookingTotal()` (`features/booking/pricing.ts`). No valid
`basePrice` -> the page refuses to quote. `/api/orders/create`
recomputes the total from `pricing_config` and rejects a mismatch.
The settings API and form fill only MISSING values (`?? 50` / `?? 10`;
a stored 0 extra-day price stays 0, fixed 2026-10-10).

## Middleware
`src/middleware.ts` wraps `clerkMiddleware`. `getSubdomain()` (duplicated
in `tenant-context-supabase.ts`) handles `.localhost`, returns null for
`.vercel.app`, and otherwise treats any host with >2 dot-parts as
having a subdomain. It only sets `x-subdomain`/`x-is-main-domain`
headers; booking resolves the agency from route params. Real
subdomain routing requires a custom domain with a wildcard DNS record;
the expired domain is why none exists today.
